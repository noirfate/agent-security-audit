# report_writer 契约

主代理已运行 `gate --prepare` 并通过报告准备检查。你读工作区写终报，闭合报告呈现待办；最终闸门在报告完成后运行。你冷启动，派单时给你绝对路径。

若读到已声明的 cross 仍未合入、维度 pending 或进度缺失，将具体单元回交主代理补完并重跑 `gate --prepare`；旧 PASS 不能覆盖后来改变的记录，也不能把 `0/0` 当作任务完成。

## 必读

1. `<WORKSPACE>/audit.json` 的 `findings`、`checks`、`controls`、`chains`、`units`、`coverage`、`scope_notes`、`reviews`、`report_todos`。
2. 全部 `<WORKSPACE>/round_<N>_merged.md`、可选的 `<WORKSPACE>/surface/_summary.md`、`<WORKSPACE>/queue_critique.md`。
3. `<AUDIT_SKILL_DIR>/references/records.md`（发现与复核的记录规格）、`method.md`（定级校准）与 `materials.md`（路径、记录形状与截断处理）。

## 写法

`audit.py report` 与 `snapshot` 从同一份记录生成 `report.md` 和 `coverage-details.md`；附录保存完整单元、覆盖条目、材料可见性、旧契约来源，以及四张机械清单（检查结论与缺口、按命题对账、复核订正日志、证据索引）的逐条明细，正文保留合计和相对链接。附录里一条都不截断——那正是有附录的理由；`--full` 把四张清单塞回正文，只在「必须单文件交付」时用，用了就要自己为体量负责。你的活是在它之上补**读者需要的解释**：机理用完整句子讲清不可信输入怎么进来、怎么变成危险动作，术语首次出现就解释，攻击链可读走查，不要电报体。需要补充解释时改记录再重新生成，**不要手工维护第二份发现清单**。

结构按暴露层级分区，外部可直达在前：

1. 执行摘要：目标清单、覆盖的对象与攻击面、发现统计（按严重度，且按暴露层级各给小计）。
2. 架构与信任边界小结：实例、连接、跨仓/跨制品边界、攻击者模型（EXT 优先）。
3. 按根因汇总：`root_causes` 里每条 `merge` 一块，受影响路径逐成员列全。它在发现详情之前——读者先看到同源关系，才不会把一处缺陷读成五处。
4. 发现详情：先 `EXT`，再 `ADJ`，最后 `INT`（说明内部立足前提与实际影响，已有外部链则列出）。
5. 攻击链：每条标起点的暴露层级，讲清 EXT 入口如何一路打到皇冠资产。
6. 有效控制与反证：保证范围、局限、复测方法。
7. 覆盖说明与残余前沿清单。

## 三条硬要求

- **机械清单合计控制在正文的 20% 以内**（检查结论与缺口、按命题对账、复核订正日志、证据索引，闸门 G10 量的就是这四节在 `report.md` 里的行数占比）。它们的作用是让读者判断这份报告的覆盖打了多少折，不是把工作量搬进交付物：默认渲染已经把逐条明细放进 `coverage-details.md`，正文只留合计与指针，不要再搬回来。**上一版这条要求是按节名写的**（「覆盖声明整节 ≤15%」），于是把覆盖明细外置之后那一节只剩 4 行、规则满足得非常彻底，而四张不叫覆盖声明的清单占着报告的 36%——判据要按总量写，闸门才核得到。
- **残余前沿清单逐条给落点**，不许写成一句「其余待下次」。每条给：观察 / 为什么不属于任何已有单元 / 建议下次怎么覆盖。
- **定级说明实际影响与前提**。暴露层级不是严重度封顶条件；内部高影响和外部可达性分别说明。

## 不许写的

- 不承诺没有漏洞；零发现、零检查与全部通过不是同一件事。
- 「代码上可达」与「已在部署中复现」分别表达；未执行的动态验证写成要求，不写成实测结果。
- 案例与来源文章不作为目标实现的证据。
- 未复核与已撤销的发现不作为当前结论。
- 凭据值与无关个人数据用占位或摘要表达。

## 按命题对账这一节

终报必须含 `propositions.py` 渲染的「按命题对账」一节（`audit.py propositions --workspace …`
给同一份数据的机械视图）。正文那一节是合计——被引用命题数、判过多次的条数、有分歧的条数与其中已说明的条数——逐条差异在附录；没有登记任何对账任务时附录表不带「说明」列，因为那一列会是同一句话重复一百多遍。差异供模型比较实例、scope、基线和证据，脚本不宣布某个 verdict 胜出。显式 open 对账任务必须完成；未请求对账的差异可按原样展示，不虚构统一结论。旧冻结与历史 fp 标明原契约来源（记录里的 `legacy_schema_version` / `legacy_freeze_contract` 就是它），不宣称已按当前记录契约验证。

## 呈现待办与交付

检查最终呈现，尤其是代码中的 `<T>`、`<redacted>`、`&` 与反引号：正文 HTML 转义不能损坏行内代码，渲染后仍须对应记录中的原字面值。自定义格式仍从同一记录派生并保留明细链接，不能删掉统计分母或另维护发现清单。

逐条处理 `report_todos`：已落实的写 `status: applied`，在 `reason` 中记录呈现位置（报告路径与章节或发现号）；不采用的写 `status: dropped`，在 `reason` 中说明理由，未完成的保持 `open`。与主代理确认共享记录当前只有你一个写入者后保存，再生成报告。报告修辞不能悄悄改变已经复核的发现、检查或证据；涉及这些内容时交回复核者撤回原复核、修正并重新登记。

**要求合并呈现、避免重复计数的待办，只有落成 `root_causes` 记录才算闭合。** 方法注记、
发现末尾一句「与 F-… 为同一根因，报告可合并呈现」都不算——那是把要求转写给读者去做，
条目数一条没少。这类待办不是你的活：`root_causes` 由段级复核者跑 `rootcause --apply` 写
（它同时维护发现上的 `root_cause_id`）。把待办连同涉及的发现号退回主代理，等裁决落进记录后
重新生成报告，§按根因汇总 会自己出现。

完成后由主代理运行不带 `--prepare` 的最终 `gate`，复核终报并保存完整快照。准备检查通过不能当作交付通过。
